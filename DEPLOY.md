# Развёртывание проекта «ЖКС»

## Основная схема

Сайт — статическая сборка Astro. Основной адрес публикации — https://jks.ooo на NIC.RU; админка — https://jks.ooo/admin. Она пишет данные в GitHub через API, после чего Actions пересобирает сайт. GitHub Pages https://nextangel-git.github.io остаётся зеркалом. Express в `admin/` — отдельная локальная опция. VPS не требуется; инструкция для него оставлена в `DEPLOY-VPS.md`.

Историческое демо https://jks-sosnovoborsk.surge.sh не является основным SEO-адресом. В конфигурации основной origin уже https://jks.ooo; факт загрузки и проверки конкретного выпуска фиксируется в SUMMARY.md. Автоматическая отправка на NIC.RU пока не активирована: GitHub Secrets не созданы, `NIC_DEPLOY_ENABLED` не включён. До отдельного разрешения и настройки автообновления сохранения в админке обновляют GitHub/Pages, а NIC.RU обновляется ручной публикацией.

## Локальная разработка и проверка

Node.js 24, npm. Git-репозиторий находится в `jks-site`; соседние `migration/`, `references/` и `presentation/` в него не входят.

```bash
npm ci
npm ci --prefix admin
npm test
python -m unittest discover -s tests -p test_deploy_nic.py
npm run build
npm run test:build
npm run preview -- --host 127.0.0.1
```

Для разработки — `npm run dev`. Сборка лежит в `dist/`. Публикуются только файлы `dist/`, никогда корень репозитория, `admin/users.json`, `.secret` или `.env`.

## Сборка GitHub Actions и зеркало Pages

Push в `main` запускает `.github/workflows/deploy.yml`: установка по lockfile, тесты, сборка, проверка готового артефакта, публикация Pages. Pull request выполняет проверки без публикации. Ручной запуск доступен через Actions → Build & Deploy → Run workflow. Фактическое завершение проверяют по статусу Actions; время сборки не гарантируется.

Единый адрес сборки задаётся через `SITE_URL` в окружении, по умолчанию `https://jks.ooo`. Из него формируются canonical, schema.org, sitemap и robots.txt. Для Actions используется Repository variable `SITE_URL`, если она задана; старое переопределение на Pages нужно удалить или заменить перед выпуском. Для локальной сборки в PowerShell:

```powershell
$env:SITE_URL = 'https://jks.ooo'
npm run build
```

`/admin`, `/404` и клиентская оболочка `/house` имеют `noindex` и исключены из sitemap. Карточки домов продолжают открываться по `/house?street=…&num=…`; отдельных индексируемых страниц домов пока нет. Robots разрешает обход, чтобы поисковик мог прочитать `noindex`; это не средство защиты админки.

## Ручная публикация на NIC.RU

Публикатор `scripts/deploy-nic.py` использует стандартную библиотеку Python и FTPS с проверкой сертификата: соединение с `ftp.jksooo.nichost.ru:21`, TLS SNI/hostname `jksooo.nichost.ru`, защищены управляющий канал и передача данных. FTP-корень `/` соответствует `/home/jksooo/jks.ooo/docs`.

Перед первой публикацией ответственное лицо сохраняет и проверяет резервную копию старого сайта на компьютере, затем отдельно очищает webroot. Скрипт деплоя старый сайт не удаляет. В окружении процесса должны быть `NIC_FTP_HOST`, `NIC_FTP_USER`, `NIC_FTP_PASSWORD`, `NIC_FTP_TLS_NAME`; значения пароля и логина передаются из защищённого источника, не записываются в исходники или команды документации.

Только после проверки backup и абсолютно пустого FTP-корня выполняется одноразовая инициализация:

```powershell
python scripts/deploy-nic.py --initialize
```

Она создаёт только `.jks-deploy-target.json`, проверяет пустоту через MLSD и отказывается работать при любых оставшихся файлах/каталогах, включая скрытые. При обычном обновлении `--initialize` не нужен.

После успешных тестов и сборки с origin jks.ooo:

```powershell
$env:SITE_URL = 'https://jks.ooo'
npm run build
npm run test:build
python scripts/deploy-nic.py --dist dist
```

Публикатор требует marker с доменом и ожидаемым серверным путём. Файлы загружаются под уникальными временными именами и заменяются rename: сначала ресурсы, затем HTML, последним `.htaccess`. Manifest фиксирует владение файлами и позволяет продолжить прерванную загрузку; целиком весь сайт одной атомарной операцией не переключается. После публикации удаляются только прежние управляемые файлы, отсутствующие в новом выпуске, если их SHA-256 не изменился вручную. Старые `_astro/` сохраняются для кеша. Чужие файлы не удаляются; коллизия с новым файлом выпуска останавливает публикацию. Скрипт не удаляет каталоги рекурсивно.

После публикации проверить HTTPS, главную, `/about`, `/admin`, карточку дома, MIME/UTF-8, настоящий 404, robots/sitemap и запрет HTTP-доступа к dotfiles. Для отката собрать проверенный прежний Git-коммит и опубликовать его тем же способом; восстановление старого Bitrix из backup является отдельной операцией.

## Автоматическая публикация NIC.RU — подготовлена, не включена

Workflow содержит отдельную job `deploy-nic` после проверок `build`. Она скачивает уже проверенный артефакт `github-pages`, распаковывает его в dist и вызывает тот же скрипт. Условие запуска: `NIC_DEPLOY_ENABLED == 'true'`, ветка `main`, событие push либо ручной workflow_dispatch; pull request не публикуется.

Для активации после отдельного разрешения нужны GitHub Secrets `NIC_FTP_HOST`, `NIC_FTP_USER`, `NIC_FTP_PASSWORD`, `NIC_FTP_TLS_NAME`, проверенный marker на сервере и Repository variable `NIC_DEPLOY_ENABLED=true`. В текущем шаге секреты не создаются, переменная не включается. Публикации сериализованы и не отменяют уже выполняющуюся FTPS-загрузку.

## Документы старого сайта

Read-only проверка перед подготовкой выпуска: `src/data/documents.json` содержит 0 записей, `public/documents/` и `dist/documents/` пусты. Соседний `migration/public/documents/old/` существует, но файлов в нём нет. Старое упоминание 108 файлов/148 МБ в исторических заметках не означает наличие этих документов в поставке.

Пустота намеренная: коммит `6e6f518fc9a5b21af5a1f7fd3e6710b35e9e2227` от 17.11.2026 («чистый старт») заменил 94 документа пустым массивом и зафиксировал в SUMMARY решение Дениса о наполнении с нуля. Позднее один тестовый документ добавлен в `6a2fcb6` и удалён в `9d7ca71`. Случайная потеря коллекции при текущем аудите не обнаружена; прежний контент автоматически не возвращается.

В `migration/` найдены 12 документов общим объёмом 2 164 098 байт (прайсы и расчёты), это другой набор. В `_backups/old_site_2026-11-19/` хранятся материалы резервирования старого Bitrix; они не копируются автоматически в сайт и не входят в dist. Документы из backup должны быть отдельно извлечены, отобраны, проверены и привязаны в JSON, если УК решит их опубликовать. Этот шаг не выполнялся; новая публикация сама по себе не восстанавливает прежние 148 МБ.

## Переезд на домен или другой статический хостинг

1. Согласовать домен, хостинг и основной HTTPS-адрес, проверить права владельца.
2. При GitHub Pages — настроить Custom domain и HTTPS в Settings → Pages, DNS по [инструкции GitHub](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site). Для корневого домена не использовать обычный CNAME; допустимые A/AAAA либо ALIAS/ANAME выбираются по документации провайдера и GitHub.
3. Изменить `SITE_URL`, пересобрать и проверить адреса в `robots.txt`, sitemap и HTML. Домен/CNAME в текущем аудите не добавлялись.
4. На другом хостинге обеспечить `/about` → `about/index.html`, настоящий HTTP 404 через `404.html`, HTTPS, правильные MIME-типы. Загружать сборку целиком. Для NIC.RU процесс описан выше; для других хостингов потребуется отдельная настройка доставки `dist/`.
5. Сверить `migration/redirects-map.md` и нужные редиректы со старого сайта. Каталог документов сейчас пуст; старые скачанные документы не являются частью поставки.
6. Обновить SUMMARY.md, AGENTS.md и инструкции после фактического переключения адреса.

## Основная статическая админка

Первичная настройка в браузере: fine-grained GitHub PAT с доступом только к репозиторию, Contents: Read and write, затем собственный пароль. PAT хранится в localStorage в зашифрованном виде (AES-GCM/PBKDF2). Последующие входы: пароль и Яндекс SmartCaptcha. 2FA отключена по решению владельца. Проверка капчи клиентская и не заменяет права GitHub.

Файлы до 25 МБ загружаются через Git Data API. При смене компьютера, браузера, домена или очистке localStorage нужна новая привязка. При передаче владельцу нужно также обновить OWNER/REPO в `src/lib/github-admin.js` — см. `HANDOVER.md`.

## Локальная серверная админка (опция)

```bash
cd admin
npm ci
npm start
```

Адрес по умолчанию — http://127.0.0.1:4777. Вход: логин, пароль, SVG-капча; 2FA не требуется. Пользователи создаются командой `node server.mjs --add-user <логин> <имя> <пароль>`, пароль меняется через `--passwd`. Не хранить реальные пароли в скриптах или документации. `admin/users.json` и `.secret` не коммитятся. Сессии находятся в памяти процесса: после перезапуска нужен повторный вход.

Сохранение меняет локальные JSON и создаёт Git-коммит; по умолчанию выполняется push. `GIT_PUSH=0` отключает отправку. `REBUILD=1` включает локальную пересборку. Для изолированной проверки используйте тесты проекта, а не рабочие данные.

## Сверка домов и VK

Скрипты находятся в соседнем `migration/`; обычный clone репозитория их не содержит. Для mingkh нужен Python с `beautifulsoup4` (`python -m pip install -r requirements-sync.txt` из migration). Ручной запуск: `python mingkh_sync.py`. Скрипт изменяет данные и при успешной сборке делает commit/push. Для публикации требуются чистая `main` и совпадение с `origin/main`; незапушенные локальные коммиты останавливают автоматизацию. `--no-push` сохраняет данные и сборку только локально. Ни один из режимов не является безвредной проверкой.

Изолированная проверка без сети и настоящих данных: `python -m unittest -v test_mingkh_sync.py` из migration. Обработка выполняется на временной копии; при ошибке rebuild/build до коммита JSON восстанавливаются, исходный snapshot обновляется последним. После неудачного push нужно разобраться с созданным коммитом вручную. Если процесс аварийно прерван, перед следующим запуском проверить JSON и `.mingkh-sync.lock`; удалять lock только убедившись, что синхронизация не работает. Автоматизация на компьютере настраивается отдельно; в GitHub Actions ежемесячного синка нет. Состояние существующего расписания проверяется отдельно.

## Форма заявки

Получатель FormSubmit — `uk@jks.ooo` (выбор владельца 19.11.2026); переопределение — публичная переменная `PUBLIC_FORM_TARGET` при сборке. В Actions она задаётся Repository variable, локально — `.env` по примеру `.env.example`.

До приёмки необходимо активировать этот адрес в FormSubmit и подтвердить доставку контрольной заявки владельцем почты УК. Аудит сам писем не отправляет. При ошибке автоотправки доступно готовое письмо через `mailto:`; для него нужен настроенный почтовый клиент. Статус заявки не интегрирован с личным кабинетом, обращения не записываются в `requests.json`.

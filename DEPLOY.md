# Развёртывание проекта «ЖКС»

## Основная схема

Сайт — статическая сборка Astro. Текущий адрес: https://nextangel-git.github.io. Основная админка: https://nextangel-git.github.io/admin; она пишет данные в GitHub через API, после чего Actions пересобирает сайт. Express в `admin/` — отдельная локальная опция. VPS не требуется; инструкция для него оставлена в `DEPLOY-VPS.md`.

Домен `jks.ooo` пока не переключён этой работой. Демо-зеркало `https://jks-sosnovoborsk.surge.sh` не является основным SEO-адресом.

## Локальная разработка и проверка

Node.js 24, npm. Git-репозиторий находится в `jks-site`; соседние `migration/`, `references/` и `presentation/` в него не входят.

```bash
npm ci
npm ci --prefix admin
npm test
npm run build
npm run test:build
npm run preview -- --host 127.0.0.1
```

Для разработки — `npm run dev`. Сборка лежит в `dist/`. Публикуются только файлы `dist/`, никогда корень репозитория, `admin/users.json`, `.secret` или `.env`.

## GitHub Pages

Push в `main` запускает `.github/workflows/deploy.yml`: установка по lockfile, тесты, сборка, проверка готового артефакта, публикация Pages. Pull request выполняет проверки без публикации. Ручной запуск доступен через Actions → Build & Deploy → Run workflow. Фактическое завершение проверяют по статусу Actions; время сборки не гарантируется.

Единый адрес сборки задаётся через `SITE_URL` в окружении, по умолчанию `https://nextangel-git.github.io`. Из него формируются canonical, schema.org, sitemap и robots.txt. Для Actions используется Repository variable `SITE_URL`. Для локальной сборки в PowerShell:

```powershell
$env:SITE_URL = 'https://jks.ooo'
npm run build
```

Не менять основной адрес до согласованного переноса. `/admin`, `/404` и клиентская оболочка `/house` имеют `noindex` и исключены из sitemap. Карточки домов продолжают открываться по `/house?street=…&num=…`; отдельных индексируемых страниц домов пока нет. Robots разрешает обход, чтобы поисковик мог прочитать `noindex`; это не средство защиты админки.

## Переезд на домен или другой статический хостинг

1. Согласовать домен, хостинг и основной HTTPS-адрес, проверить права владельца.
2. При GitHub Pages — настроить Custom domain и HTTPS в Settings → Pages, DNS по [инструкции GitHub](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site). Для корневого домена не использовать обычный CNAME; допустимые A/AAAA либо ALIAS/ANAME выбираются по документации провайдера и GitHub.
3. Изменить `SITE_URL`, пересобрать и проверить адреса в `robots.txt`, sitemap и HTML. Домен/CNAME в текущем аудите не добавлялись.
4. На другом хостинге обеспечить `/about` → `about/index.html`, настоящий HTTP 404 через `404.html`, HTTPS, правильные MIME-типы. Загружать сборку целиком. Изменения через админку попадут в GitHub, но на сторонний хостинг нужен отдельный настроенный процесс доставки `dist/`; текущий workflow публикует только GitHub Pages.
5. Сверить `migration/redirects-map.md` и нужные редиректы со старого сайта. Каталог документов сейчас пуст; старые скачанные документы не являются частью поставки.
6. Обновить SUMMARY.md, AGENTS.md и инструкции после фактического переключения адреса.

## Основная статическая админка

Первичная настройка в браузере: fine-grained GitHub PAT с доступом только к репозиторию, Contents: Read and write, затем собственный пароль. PAT хранится в localStorage в зашифрованном виде (AES-GCM/PBKDF2). Последующие входы: пароль и Яндекс SmartCaptcha. 2FA отключена по решению владельца. Проверка капчи клиентская и не заменяет права GitHub.

Файлы до 25 МБ загружаются через Git Data API. При смене компьютера, браузера, домена или очистке localStorage нужна новая привязка. При передаче владельцу нужно также обновить OWNER/REPO в `src/lib/github-admin.js` — см. `HANDOVER.md`.

## Локальная серверная админка (опция)

```bash
cd admin
npm ci
npm start
```

Адрес по умолчанию — http://127.0.0.1:4777. Вход: логин, пароль, SVG-капча; 2FA не требуется. Пользователи создаются командой `node server.mjs --add-user <логин> <имя> <пароль>`, пароль меняется через `--passwd`. Не хранить реальные пароли в скриптах или документации. `admin/users.json` и `.secret` не коммитятся. Сессии находятся в памяти процесса: после перезапуска нужен повторный вход.

Сохранение меняет локальные JSON и создаёт Git-коммит; по умолчанию выполняется push. `GIT_PUSH=0` отключает отправку. `REBUILD=1` включает локальную пересборку. Для изолированной проверки используйте тесты проекта, а не рабочие данные.

## Сверка домов и VK

Скрипты находятся в соседнем `migration/`; обычный clone репозитория их не содержит. Для mingkh нужен Python с `beautifulsoup4` (`python -m pip install -r requirements-sync.txt` из migration). Ручной запуск: `python mingkh_sync.py`. Скрипт изменяет данные и при успешной сборке делает commit/push. Для публикации требуются чистая `main` и совпадение с `origin/main`; незапушенные локальные коммиты останавливают автоматизацию. `--no-push` сохраняет данные и сборку только локально. Ни один из режимов не является безвредной проверкой.

Изолированная проверка без сети и настоящих данных: `python -m unittest -v test_mingkh_sync.py` из migration. Обработка выполняется на временной копии; при ошибке rebuild/build до коммита JSON восстанавливаются, исходный snapshot обновляется последним. После неудачного push нужно разобраться с созданным коммитом вручную. Если процесс аварийно прерван, перед следующим запуском проверить JSON и `.mingkh-sync.lock`; удалять lock только убедившись, что синхронизация не работает. Автоматизация на компьютере настраивается отдельно; в GitHub Actions ежемесячного синка нет. Состояние существующего расписания проверяется отдельно.

## Форма заявки

Получатель FormSubmit — `uk@jks.ooo` (выбор владельца 19.11.2026); переопределение — публичная переменная `PUBLIC_FORM_TARGET` при сборке. В Actions она задаётся Repository variable, локально — `.env` по примеру `.env.example`.

До приёмки необходимо активировать этот адрес в FormSubmit и подтвердить доставку контрольной заявки владельцем почты УК. Аудит сам писем не отправляет. При ошибке автоотправки доступно готовое письмо через `mailto:`; для него нужен настроенный почтовый клиент. Статус заявки не интегрирован с личным кабинетом, обращения не записываются в `requests.json`.

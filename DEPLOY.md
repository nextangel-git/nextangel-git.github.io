## Основная схема

Постоянный FTPS-доступ GitHub Actions одобрен владельцем: четыре NIC_FTP-секрета записаны, `NIC_DEPLOY_ENABLED=true`. Ручной запуск на main `9e970f3` завершился успешно: [Actions 44451430532](https://github.com/nextangel-git/nextangel-git.github.io/actions/runs/44451430532), jobs build, deploy и deploy-nic — success. ## Локальная разработка и проверка

Node.js 24, npm, Python 3 и PHP с расширением curl для проверки серверной админки. Git-репозиторий находится в `jks-site`; соседние `migration/`, `references/`, `presentation/` и `_ops/` в него не входят. CI использует предустановленный PHP 8.3 на Ubuntu 24.04; локальная проверка может использовать отдельный portable PHP. Composer не требуется.

```bash
npm ci
npm ci --prefix admin
npm test
python -m unittest discover -s tests -p test_deploy_nic.py
npm run build
npm run test:build
npm run preview -- --host 127.0.0.1
```

Для разработки публичных страниц — `npm run dev`; он не исполняет PHP. Сборка лежит в `dist/`. Публикуются только файлы `dist/`, включая шесть разрешённых PHP-файлов: `api/admin.php`, `api/admin-core.php`, `api/admin-schema.php`, `api/captcha-core.php`, `api/request.php`, `api/request-core.php`. Корень репозитория, `admin/users.json`, `.secret`, `.env`, серверный config.php, сессии и rate-limit не входят в артефакт.

## Сборка GitHub Actions и зеркало Pages

Push в `main` запускает `.github/workflows/deploy.yml`: установка по lockfile, тесты, сборка, проверка готового артефакта, публикация Pages. Pull request выполняет проверки без публикации. Ручной запуск доступен через Actions → Build & Deploy → Run workflow. Фактическое завершение проверяют по статусу Actions; время сборки не гарантируется.

Единый адрес сборки задаётся через `SITE_URL` в окружении, по умолчанию `https://jks.ooo`. Из него формируются canonical, schema.org, sitemap и robots.txt. Для Actions используется Repository variable `SITE_URL`, если она задана; старое переопределение на Pages нужно удалить или заменить перед выпуском. Для локальной сборки в PowerShell:

```powershell
$env:SITE_URL = 'https://jks.ooo'
npm run build
```

`/admin`, `/404` и клиентская оболочка `/house` имеют `noindex` и исключены из sitemap. Карточки домов продолжают открываться по `/house?street=…&num=…`; отдельных индексируемых страниц домов пока нет. Robots разрешает обход, чтобы поисковик мог прочитать `noindex`; это не средство защиты админки.

В опубликованной `.htaccess` HTML-файлам задан `Cache-Control: no-cache, max-age=0, must-revalidate`, включая index.html для адресов без расширения. Живые заголовки подтверждены после успешного Actions №44455083387 (код193509d); PHP API сохраняет no-store, ресурсы с хешами продолжают кешироваться. Уже закешированная старая HTML может потребовать однократного обновления страницы.

## Ручная публикация на NIC.RU

Публикатор `scripts/deploy-nic.py` использует стандартную библиотеку Python и FTPS с проверкой сертификата: соединение с `ftp.jksooo.nichost.ru:21`, TLS SNI/hostname `jksooo.nichost.ru`, защищены управляющий канал и передача данных. FTP-корень `/` соответствует `/home/jksooo/jks.ooo/docs`.

Перед первой публикацией ответственное лицо сохраняет и проверяет резервную копию старого сайта на компьютере, затем отдельно очищает webroot. Скрипт деплоя старый сайт не удаляет. В окружении процесса должны быть `NIC_FTP_HOST`, `NIC_FTP_USER`, `NIC_FTP_PASSWORD`, `NIC_FTP_TLS_NAME`; значения пароля и логина передаются из защищённого источника, не записываются в исходники или команды документации.

Только после проверки backup и абсолютно пустого FTP-корня выполняется одноразовая инициализация:

```powershell
python scripts/deploy-nic.py --initialize
```

Она создаёт только `.jks-deploy-target.json`, проверяет пустоту через MLSD и отказывается работать при любых оставшихся файлах/каталогах, включая скрытые. При обычном обновлении `--initialize` не нужен.

После успешных тестов и сборки с origin jks.ooo:

```powershell
$env:SITE_URL = 'https://jks.ooo'
npm run build
npm run test:build
python scripts/deploy-nic.py --dist dist
```

Публикатор требует marker с доменом и ожидаемым серверным путём. Файлы загружаются под уникальными временными именами и заменяются rename: сначала ресурсы, затем HTML, последним `.htaccess`. Manifest фиксирует владение файлами и позволяет продолжить прерванную загрузку; целиком весь сайт одной атомарной операцией не переключается. После публикации удаляются только прежние управляемые файлы, отсутствующие в новом выпуске, если их SHA-256 не изменился вручную. Старые `_astro/` сохраняются для кеша. Чужие файлы не удаляются; коллизия с новым файлом выпуска останавливает публикацию. Скрипт не удаляет каталоги рекурсивно.

После публикации проверить HTTPS, главную, `/about`, `/admin`, карточку дома, MIME/UTF-8, настоящий 404, robots/sitemap и запрет HTTP-доступа к dotfiles. Для отката собрать проверенный прежний Git-коммит и опубликовать его тем же способом; восстановление старого Bitrix из backup является отдельной операцией.

## Переезд на домен или другой хостинг

1. Согласовать домен, хостинг и основной HTTPS-адрес, проверить права владельца.
2. При GitHub Pages — настроить Custom domain и HTTPS в Settings → Pages, DNS по [инструкции GitHub](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site). Для корневого домена не использовать обычный CNAME; допустимые A/AAAA либо ALIAS/ANAME выбираются по документации провайдера и GitHub.
3. Изменить `SITE_URL`, пересобрать и проверить адреса в `robots.txt`, sitemap и HTML. Домен/CNAME в текущем аудите не добавлялись.
4. На другом хостинге обеспечить `/about` → `about/index.html`, настоящий HTTP 404 через `404.html`, HTTPS, правильные MIME-типы и PHP/curl для серверной админки. Для чисто статического хостинга публичные страницы работают, но вход по логину/паролю потребует отдельного backend и согласованной доработки API. Загружать сборку целиком. Для NIC.RU процесс описан выше; для других хостингов потребуется отдельная настройка доставки `dist/`.
5. Сверить `migration/redirects-map.md` и нужные редиректы со старого сайта. Каталог документов сейчас пуст; старые скачанные документы не являются частью поставки.
6. Обновить SUMMARY.md, AGENTS.md и инструкции после фактического переключения адреса.

## Основная админка: PHP API и серверная сессия

Сотрудник входит на `https://jks.ooo/admin` с логином и паролем. PAT в браузер не вводится и не выдаётся. Браузер работает только с same-origin PHP API; после проверки учётной записи сервер обращается к фиксированному репозиторию `nextangel-git/nextangel-git.github.io`, ветка main. Произвольные URL GitHub и пути файлов от клиента не принимаются.

Сессия использует `__Host-jks_admin` с Secure, HttpOnly, SameSite=Strict и Path=/; действуют простой 30 минут и абсолютный срок 8 часов. Изменяющие запросы защищены CSRF-токеном и проверкой Origin. Пароль хранится как password_hash; смена пароля и выход ротируют состояние сессии. При смене браузера достаточно войти заново, привязка localStorage больше не требуется.

### Отдельная подготовка приватной конфигурации

На сервере, **за пределами webroot**, требуется `/home/jksooo/jks.ooo/.jks-admin/config.php`. Код получает этот путь относительно `/home/jksooo/jks.ooo/docs/api/`; в публичный каталог config копировать нельзя. Файл возвращает PHP-массив с `github_token` и `users`; каждая учётная запись содержит `password_hash`, `name`, `enabled`. Сам пароль не записывается, только хеш `password_hash(..., PASSWORD_DEFAULT)`.

19.11.2026 владелец явно разрешил использовать существующий GitHub-токен с правами `repo`, `workflow`, `gist` на NIC.RU вне webroot; начальный логин — `jksadmin`. Локальная конфигурация с хешем пароля подготовлена в `_ops/private-admin/config.php` вне репозитория сайта. Config уже размещён вне webroot с правами 0600, приватный каталог — 0700. Десять реальных API-проверок прошли успешно: в том числе вход jksadmin, чтение GitHub, CSRF и выход. Ограниченный одноразовый установщик подтвердил self_deleted=true; повторный HTTP-запрос вернул 404. Новый интерфейс опубликован и проверен в живом браузере; подробности выпуска — в SUMMARY.md. Рекомендуемая дальнейшая замена — отдельный fine-grained PAT с Contents: Read and write только для репозитория сайта. FTP-секреты Actions и серверный PAT выполняют разные задачи и не заменяют друг друга. Provisioning, передача начального пароля и проверка входа не выполняются сборкой или FTPS-деплоем; значения секретов в Git не помещаются.

Для первоначального создания конфигурации предусмотрен локальный CLI `admin/provision-php.php`. Он принимает JSON из stdin с ключами `username`, `name`, `password`, `github_token` либо переменные `JKS_ADMIN_USERNAME`, `JKS_ADMIN_NAME`, `JKS_ADMIN_PASSWORD`, `JKS_GITHUB_TOKEN` без `--stdin`. Пароль и токен не передаются аргументами командной строки. Пример команды на сервере с необходимым доступом, при уже подготовленном защищённом stdin:

```bash
php admin/provision-php.php --output=/home/jksooo/jks.ooo/.jks-admin/config.php --stdin
```

При запуске на компьютере вместо серверного пути указать абсолютный путь в закрытом каталоге вне public/dist. CLI не использует сеть, не перезаписывает существующий config, сохраняет хеш пароля и выводит только факт создания, путь и логин (`uploaded:false`). Перенос созданного файла в приватный серверный каталог — отдельная операция через административный канал, имеющий доступ выше docs; ограниченный FTP-пользователь деплоя этого сделать не может. Начальный пароль передаётся сотруднику отдельно, не добавляется в документы.

Каталог `.jks-admin` должен быть доступен PHP-процессу для записи сессий, защиты от перебора и атомарной смены пароля в конфигурации; доступ остальных пользователей ограничивается. Рекомендуемые права при совпадающем владельце: каталог 0700, config.php 0600. Конфигурация, сессии и rate-limit резервируются отдельно в закрытом хранилище, не в Git. FTP-пользователь деплоя ограничен `docs/`, поэтому соседний `.jks-admin/` не затрагивается при публикации/удалении stale-файлов.

На NIC.RU 19.11.2026 подтверждены PHP 8.5.12 (вместо 7.4), UTF-8, curl и `post_max_size=64M`. Общий `memory_limit=64M`; commit после авторизации и CSRF-проверки повышает лимит текущего запроса до 256M до чтения JSON. Более высокий или unlimited лимит не уменьшается. При запрете повышения возвращается `503 upload_memory_limit`; вход, сессии и чтение продолжают работать. Общие php.ini и .user.ini не менялись. Документ до 25 МиБ передаётся в base64; при смене хостинга требуется `post_max_size >= 40M` и возможность выделить commit-запросу 256M. До provisioning API возвращал `503 not_configured`; после размещения config вход и чтение подтверждены.

### Проверка после provisioning и публикации

Выполнены десять реальных API-проверок и браузерная проверка входа/чтения/выхода. Реальная запись в main не выполнялась: автоматическая проверка разрешений отклонила тестовый пустой коммит как лишнюю мутацию рабочего репозитория. Этот запрет не обходили. Запись, конфликт SHA и атомарное создание Git-коммита проверены изолированными тестами с mock GitHub; полный рабочий цикл сохранения остаётся до первого согласованного изменения контента.

- Неавторизованный запрос не читает и не меняет данные репозитория.
- Вход с неверным паролем отклоняется, ограничение перебора работает.
- Успешный вход выдаёт защищённую cookie; PAT отсутствует в ответах и browser storage.
- Запрос без CSRF либо с чужим Origin отклоняется.
- Проверены смена пароля, выход, истечение сессии и конфликт сохранения.
- После согласованного изменения появился Git-коммит, Actions завершил NIC-деплой, запись видна на сайте.

## Сверка домов и VK

Текущий серверный процесс — PHP CLI из `server/sync/`, установленный отдельно от публичного сайта в `/home/jksooo/jks.ooo/.jks-admin/sync/`. В панели [cron NIC.RU](https://www.nic.ru/hcp2/cron/) создана задача **в пробном режиме dry-run**. Включение автоматической записи в GitHub и успешная работа боевого расписания пока не подтверждены. Исходники в Git не означают, что их новая версия уже установлена на сервере.

Настройка задачи: интерпретатор PHP конфигурации сайта `jks.ooo`, файл `/home/jksooo/jks.ooo/.jks-admin/sync/cron.php`, запуск каждый час в 17 минут (`17 * * * *`). Нужны PHP 8.1+ с curl, DOM и iconv. Node.js, Python, Git и включённый локальный компьютер серверной задаче не нужны. В GitHub Actions сборка запускается после коммита; расписания сбора источников там нет.

Внутри PHP VK проверяется раз в час. Для mingkh после первого успешного рабочего сбора действует срок 5-го числа месяца в 10:17, часовой пояс `Asia/Krasnoyarsk`; пропущенный срок догоняется ближайшим часовым запуском. Первый сбор и смена режима dry-run/рабочий выполняются без ожидания месячной даты. В текущем dry-run сохраняется `last_preview`, а не `last_success`: пока рабочего успеха нет, mingkh может повторяться каждый час. Это поведение пробного режима, а не подтверждение ежемесячной публикации.

В приватной папке находятся `cron.php`, `core.php`, `vk.php`, `mingkh.php` и `settings.json`; каталог имеет права 0700, файлы — 0600. Настройки на этапе проверки: `{"dry_run":true,"vk":true,"mingkh":true}`. GitHub-токен читается из существующего `../config.php`; его не копируют в настройки или строку команды. Состояние, preview и snapshot также остаются вне docs. Обычный FTPS-деплой `dist` эту папку не обновляет.

Dry-run читает источники и GitHub, сохраняет `vk-preview.json`/`mingkh-preview.json` при наличии отличий и `*-status.json`, но не создаёт коммиты. Перед переходом на `dry_run:false` проверить закрытые отчёты, расхождения УК, полноту карточек и отключение старых локальных запусков. Переход в рабочий режим — отдельный шаг; эта инструкция не утверждает, что он выполнен. В рабочем режиме допустимы только атомарные изменения `src/data/vk_posts.json`, `src/data/houses_geo.json`, `src/data/competitors.json` и журнала в SUMMARY.md. Состав домов ЖКС и известные координаты автоматически не меняются. Конфликт GitHub HEAD останавливает запись без force; статус `committed` ещё не означает завершённую сборку и доставку — нужно проверить Actions.

Общий `flock` исключает одновременные серверные запуски и освобождается при завершении процесса. Ключи `--dry-run`, `--only=vk`, `--only=mingkh`, `--force` предназначены для сопровождения; `--force` обходит срок запуска, но не отменяет dry-run и проверки данных. Подробности — [server/sync/README.md](server/sync/README.md). Для остановки автоматизации отключить задачу в NIC.RU; приватные файлы состояния сохраняются для разбора.

### Прежние локальные точки запуска: история и предотвращение дублей

До переноса использовались соседние `migration/mingkh_sync.py` и `migration/vk_extract.py`; обычный clone репозитория сайта их не содержит. Они также вызываются кнопками `/sync` локальной Express-админки (`admin/server.mjs`, POST `/sync/mingkh` и `/sync/vk`). Эти кнопки и старые скрипты пока сохранены; после включения серверного расписания ими не следует запускать параллельную синхронизацию. Строка локального интерфейса «автоматически 5-го числа» сама по себе не доказывает существование задания планировщика.

Исторический mingkh-скрипт требует Python/BeautifulSoup, Git и Node/npm: меняет локальные JSON, проверяет сборку и делает commit/push. `--no-push` всё равно изменяет файлы и запускает сборку, это не dry-run. Старый VK-скрипт обращается к браузерному мосту `127.0.0.1:10086` и сессии `jks-vk`, напрямую перезаписывает `vk_posts.json`, в том числе пустой выборкой; сам сборку и push не выполняет. Он не является серверным резервным способом сбора.

До боевой активации NIC нужно отдельно проверить Windows Task Scheduler, автозагрузку, внешние cron и оболочки на вызовы этих двух файлов; найденные задания экспортировать и отключить, не удаляя историю. Фактическое отключение старых заданий этим документом не подтверждается. Предлагаемое следующее усиление — явный режим «источник обновляется на NIC» с отказом старых скриптов и локальных POST `/sync/*`; исключение только для намеренного разбора в отдельной тестовой копии. Этот программный запрет пока не реализован. Для временного ручного обслуживания сначала остановить NIC-задачу, затем работать с актуальным HEAD и отдельно проверить итог публикации: локальный lock не защищает от процесса на другом компьютере.

Исторические изолированные тесты mingkh: `python -m unittest -v test_mingkh_sync.py` из migration, без сети и рабочих данных. При ошибке прежнего rebuild/build до коммита скрипт восстанавливает JSON; snapshot обновляется последним. После неудачного push требуется ручная проверка созданного коммита. Оставшийся `.mingkh-sync.lock` удаляют только после проверки, что локальный процесс уже не работает. Эти сведения сохранены для сопровождения старого инструмента и не являются инструкцией включить второй планировщик.

## Yandex SmartCaptcha: отдельная настройка

Новый код защищает форму заявки и вход `/admin`. Публичный sitekey находится в `src/lib/smartcaptcha.js`; серверный секрет требуется в `/home/jksooo/jks.ooo/.jks-admin/captcha.php`, вне docs и отдельно от GitHub config.php. Файл не входит в сборку и явно запрещён публикатором, в том числе при случайном попадании в публичный каталог. Секрет установлен 19.11.2026 в отдельный приватный файл; одноразовый установщик удалён (HTTP404), резервная копия зашифрована DPAPI вне Git. Итог публикации и живых проверок — в SUMMARY.md.

Проверка следует [контракту Yandex SmartCaptcha](https://yandex.cloud/ru/docs/smartcaptcha/concepts/validation), но при сетевой ошибке действует fail-closed: сервер требует успешный ответ, status ok и hostname jks.ooo. Недоступность сервиса, неверный токен либо отсутствие конфигурации не разрешают вход или отправку. Новый приватный файл возвращает PHP-массив с ключами `sitekey` и `secret`; sitekey должен совпадать с публичным ключом в коде, права файла — 0600 при каталоге 0700. Файл настраивается отдельным защищённым действием; существующий GitHub config.php не заменяется. Для обращения действуют лимит JSON 32 КиБ и до двадцати попыток с одного IP за 15 минут; данные обращения не пишутся в журнал капчи или Git.

Перед выпуском проверить отсутствие секрета в артефакте, отказ без/с неверным токеном без обращения к FormSubmit, отказ логина без капчи, обязательность квартиры и успешную проверку настоящего виджета. Письмо проверяется только согласованной отправкой с участием владельца почты.

## Форма заявки

В готовящемся обновлении квартира обязательна на клиенте и сервере. Браузер отправляет заявку в same-origin `/api/request.php`; PHP проверяет Yandex SmartCaptcha и только после успешной проверки передаёт письмо в FormSubmit на фиксированный `uk@jks.ooo`. Получателя нельзя изменить полем запроса или сборочной переменной; `PUBLIC_FORM_TARGET` больше не используется. Резервный mailto также адресован uk@jks.ooo.

До приёмки необходимо активировать этот адрес в FormSubmit и подтвердить доставку контрольной заявки владельцем почты УК. Аудит сам писем не отправляет. При ошибке автоотправки доступно готовое письмо через `mailto:`; для него нужен настроенный почтовый клиент. Статус заявки не интегрирован с личным кабинетом, обращения не записываются в `requests.json`.
